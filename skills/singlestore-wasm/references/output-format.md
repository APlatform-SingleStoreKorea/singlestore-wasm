# 최종 결과 형식

## 최종 결과 형식

함수 생성 요청의 최종 답변은 아래 순서로 간결하게 제공한다. 꺾쇠 안은 실제 소스·계약·`status.py` 결과로 채우며 성공을 가정하지 않는다. 일반 호출 SQL은 `validate.sql`로 안내하되, JSON 조건 배열 입력에서는 같은 공개 함수의 `JSON_BUILD_ARRAY` 호출 예시를 최종 답변에도 표시한다. 최종 결과 화면에는 성능 검증 항목을 표시하지 않는다.

```text
적용 가능성: <가능 / 조건부 가능 / 불가와 짧은 근거> — 대상 SingleStore <버전>
Wasm 생성: <성공 / 실패 / 미실행>
Base64 변환: <성공 / 실패 / 미실행>
DB 검증: <성공 / 실패 / 미실행 — 이유>

참조 출처와 원본 의미 검증:
- 공식 문서: <실제 참조 링크·버전; 미확보 시 이유>
- 원본 소스: <실제 참조 링크·고정 커밋/버전; 미확보 시 이유>
- 원본 실행: <엔진/소스 실행 방식·버전 또는 미실행 이유>
- 원본 의미 비교: <status.py의 semantic_verification 및 비교 범위; DB 검증과 별개>
- 비교 증거: <reference-verification.json 링크; 출처 링크 자체는 실행 증거가 아님>

등록 대상과 함수:
- DB: <대상 DB 이름; 미지정이면 미지정>
- 함수: <DB.함수명> — <UDF / 집계 함수(UDAF)> (<등록 완료 / 등록 예정 / 검증 후 정리>)
- 확인: <SHOW FUNCTIONS IN `DB`; 또는 SHOW AGGREGATES IN `DB`;>

반환 타입 계약:
- ABI 반환 타입: <string 등>
- SQL 반환 타입: <TEXT 등; core/public wrapper가 다르면 각각>
- 문자 집합: <utf8mb4 또는 해당 없음>
- Collation: <utf8mb4_bin 또는 해당 없음>
- NULL 정책: <NOT NULL / NULL; wrapper와 core 구분>
- WIT·SQL·Wasm 일치 여부: <정적 통과/실패/미검증>
- 실제 SingleStore 등록 검증: <통과/실패/미검증; 호출 검증 별도>

입력 계약과 제한:
- 인자: <순서대로 이름·SQL 타입·의미; 시간/금액 등 단위가 있으면 포함>
- NULL 처리: <입력 및 결과 정책>
- 지원 옵션: <옵션과 기본값; 없으면 없음>
- 선택한 지원 범위: <공개 함수 개수, SQL 인자 수, 지원 배열 길이 또는 고정 인자 범위>
- JSON 배열 호출 예시: <해당하는 경우 동일한 공개 함수에 JSON_BUILD_ARRAY로 2개·3개·5개 조건 전달>
- 빈 입력 정책: <실제 정책·원본 대비 차이·합의 근거>
- 원본 대비 차이: <공개 함수 수·호출 방식·반환 형식·계산 의미의 차이 또는 없음; 변경 합의 또는 자동 진행 정책 근거. 호출 방식 변경 시 변경 전후 예시>
- 입력 크기 한도: <문자 수·행/상태 크기 등 실제 적용 한도>

실행 환경 제약 및 검증 상태:

| 항목 | 설정·정책 | 검증 상태 |
|---|---|---|
| 외부 기능 의존성 | <파일·네트워크·프로세스·스레드 생성 등 외부 기능 의존 여부> | <소스 검사 결과 · 생성 Wasm의 Import 검사 결과> |
| 함수 메모리 | <생성된 함수의 선형 메모리 한도> | <설정 확인 여부 · 실제 사용량 측정 여부> |
| 엔진 메모리 상한 | 기본값 약 4 GiB (대상 DB에서 확인한 설정이 있으면 해당 값 표시) | <함수 설정과 비교; 기본값 기준 판단과 실제 DB 검증 여부 구분> |
| ABI·타입 호환성 | <선택한 ABI 및 인터페이스 일치 조건> | <정적 검사 결과 · DB 호출 검증 결과> |
| 등록 SQL 크기 | <생성 SQL의 바이트 수 / DB의 max_allowed_packet> | <충족 / 미충족 / 미검증과 이유> |

산출물:
- module.wasm
- module.wasm.b64

직접 실행할 SQL:
1. register.sql — 함수 등록
2. validate.sql — 실제값·기대값·통과 여부 확인
3. validate-errors.sql — 명시된 오류 코드·메시지 확인
```

실제 답변에서는 위 파일명 5개를 사용자가 바로 열 수 있는 링크로 표시한다. 파일을 찾으라고만 안내하지 않는다. Base64 본문이나 긴 등록 SQL 전체를 결과창에 붙이지 않는다.

실행 환경 표는 실제 답변에서 Markdown 표로 렌더링하고, 다음 규칙을 따른다.

- 해당 실행의 실제 산출물·DB 조회·테스트 결과로 설정값과 상태를 채운다. 예제의 16 MiB나 Canonical ABI 등을 모든 함수에 고정하지 않는다. 확인할 수 없는 값은 추정하지 않고 미검증으로 표시한다.
- 검증 상태에는 `✅ 확인·통과`, `❌ 실패·미충족`, `➖ 미검증·미수행·해당 없음`을 사용하고 구체적인 이유를 함께 적는다. 일부만 확인했으면 같은 셀에 확인 범위와 미검증 범위를 각각 표시한다.
- DB에 접속하지 않았다면 DB 설정과 실제 호출 검증은 `➖ 미검증 — DB 미접속`으로 표시한다. 상단의 `DB 검증` 결과와 표의 DB 관련 상태를 일치시킨다. 등록 성공만으로 호출 검증을 통과 처리하지 않는다.
- 메모리 설정 확인과 실제 사용량 측정, 정적 ABI 검사와 DB 호출 검증을 각각 구분한다. 하나의 성공을 다른 검증의 성공으로 표시하지 않는다.
- 등록 SQL은 해당 실행에서 전달하는 파일의 실제 바이트 수를 기록한다. DB의 `max_allowed_packet`과 비교할 때는 실제 전송 단위도 확인하고, 파일 크기와 문장별 전송 크기가 다르면 그 근거를 보고서에 남긴다. DB 값이나 비교 근거가 없으면 충족으로 단정하지 않는다.
- 입력 범위·NULL·지원 옵션은 기존 `입력 계약과 제한`에서 설명하고 표에 중복하지 않는다.
- 상세 검사 근거는 생성 프로젝트의 `verification.md` 검증 보고서에 남기고 최종 답변에서 링크한다. 사용한 산출물·검사 결과·DB 조회값·측정 조건과 단위·미검증 이유를 기록하여 표의 각 상태를 추적할 수 있게 한다.

DB 설정과 권한이 있으면 Codex가 등록·호출을 수행한다. 접속할 수 없으면 이유와 미실행/실패를 구분하고 사용자가 SQL을 순서대로 실행하도록 안내한다. `validate.sql`은 모든 `passed=1`이 정상이며, `validate-errors.sql`은 각 주석의 코드와 메시지가 일치해야 정상이다. 오류 검증은 문장별 실행하거나 오류 후에도 계속 실행하는 클라이언트를 사용한다. 오류 사례가 없는 계약은 해당 파일 링크에 '해당 없음 — 정의된 오류 사례 없음'을 표시한다. 등록 SQL 재실행은 기존 이름과 충돌하므로 이미 등록된 경우 검증 SQL부터 실행하게 한다.

DB 검증 전에는 빌드 시 `artifacts/`의 SQL 3개와 등록 예정 이름을 제공한다. DB 등록을 수행했다면 `artifacts/runs/<name>/`의 SQL 3개를 한 묶음으로 제공하고 실제 등록 이름과 맞춘다. public wrapper/core 또는 nullable 집계 등 객체가 여러 개면 사용자 호출용 이름과 내부 보조 이름을 구분한다. 검증 후 정리했다면 등록 중인 것처럼 표현하지 않는다. 실패·부분·오래된 파일을 성공 산출물로 제공하지 않는다.

스킬 자체 평가에서는 새 디렉터리에서 재현하고 예제 재사용 검증과 독립 생성 검증을 구분한다.
